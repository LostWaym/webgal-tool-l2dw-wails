# L2DW 打包与更新日志

仅在用户主动调用本 skill 时使用。根据用户要求执行打包或更新日志流程；打包前检查更新日志，未经用户同意不要修改日志。单独更新日志时不自动打包。所有项目路径均相对于项目根目录，不依赖固定的磁盘位置。

## 工具链

- Windows PowerShell、Git。
- Wails v2 CLI `wails`，以及项目所需的 Go、Node.js 和 npm。`wails build` 使用项目根目录的 `wails.json`，其中配置了前端依赖安装与构建命令。
- 7-Zip 命令行程序 `7z` 或 `7z.exe`。优先读取项目根目录 `.env` 中的 `SEVEN_ZIP_PATH`（完整可执行文件路径，参见 `.env.example`），确认文件存在；未配置或路径无效时通过 `Get-Command 7z` 查找，也可检查常见安装目录。仍找不到时请用户提供路径或安装，不要改用其他压缩格式。`.env` 是本地配置，不要执行或作为脚本加载。
- 执行外部程序后检查退出码；失败即停止并报告原因。不要因为旧产物存在而忽略构建失败。

## 打包

1. 检查 `build/bin/更新日志.txt` 的最新版本块和提交边界，按下方更新日志流程核对至当前目标提交；同时检查可能影响完整性的工作区未提交变更。边界缺失、不可信或核对范围无法确定时，不得判定日志已是最新，应说明情况并询问用户如何处理；日志缺失则停止并询问。
2. 如存在尚未记录的用户可见变化，询问用户是否先更新日志再打包；用户同意后按下方更新日志流程处理，拒绝则保留原日志并继续打包。用户已明确要求一并更新时无需重复询问。若需新增本包日志版本，先按第 5 步规则确定版本号并用于日志标题。若无法确定日志范围或版本归属，先解决歧义，不能擅自写入提交边界。
3. 在项目根目录执行 `wails build`，等待完成并检查退出码。
4. 确认 `build/bin/` 中存在 `assets/`、`l2dw-wails.exe`、`更新日志.txt`、`特别说明.txt`，缺少任何一项则停止。
5. 在 `build/bin/` 根目录扫描符合 `l2dw-wails-alpha-YYYYMMDDNN.7z` 的文件，不扫描 `archives/`。使用本地日期，取当天最大两位序号加一；当天没有匹配项时从 `00` 开始。序号超过 `99` 时停止并询问用户，不覆盖已有文件。如已为本包新增日志版本，确认版本号未变化；若已变化则停止并请用户确认日志版本处理方式。
6. 以 `build/bin/` 为工作目录，用 7-Zip 创建 `l2dw-wails-alpha-YYYYMMDDNN.7z`，只包含上述四项，归档内不要额外套一层 `bin` 目录。创建前再次检查目标不存在；不要更新或覆盖已有归档。
7. 检查压缩命令退出码，使用 `7z t` 验证归档，并检查归档文件列表确认四项齐全、没有额外的顶层项。验证失败则停止，不执行归档整理，报告异常文件。
8. 仅在新包验证成功后整理旧包，最后报告新包路径、日志检查结果和整理结果。

### 旧包归档

- 只统计 `build/bin/` 根目录中的 `.7z` 文件；数量不超过 5 时不移动。
- 超过 5 时，按文件名中的 `YYYYMMDDNN` 判断符合上述命名规则的包的版本先后，仅保留版本最新的一个，其余符合规则的包移动到 `build/bin/archives/`。其他命名的 `.7z` 不自动移动，向用户说明；因此根目录可能不止保留一个文件。
- `archives/` 不存在则创建。不要列出、读取或扫描其中的内容；移动时采用不覆盖已有文件的操作，若目标已存在或移动失败，停止并报告冲突和已经完成的移动，不删除或覆盖任何文件。

## 更新日志

目标文件为 `build/bin/更新日志.txt`。该文件可能不受 Git 跟踪，修改前保留现有内容，不重写或删除历史记录。

### 格式

- 最新版本在文件顶部，版本标题使用 `YYYYMMDDNN-alpha`，与对应发布包的版本号一致；版本块之间留空行。
- 标题下一行记录 `    Git 提交边界: <完整提交哈希>`，表示本版本日志已核对至该提交，包括该提交。记录边界不代表工作区未提交的修改已包含在 Git 中。
- 按需使用缩进四空格的分类，例如 `通用`、`预览编辑器`、`表情编辑器`、`动作编辑器`；条目缩进八空格，一条描述一个面向用户的变化，必要时说明限制或操作方式。
- 追加到已有版本时保持其原有格式；不要为了统一样式改写旧版本。已有版本无边界时，只有确认了实际核对范围才能增加边界。

### 流程

1. 先读取文件开头至最新版本块结束，通常不需要读取整个文件。若最新块没有边界，再逐块向旧版本查找最近可信的提交边界；按需扩大读取范围，不盲目通读。
2. 用 `git log` 查看从可信边界之后到当前目标提交的提交信息，例如 `git log --reverse --format='%H %s%n%b' <边界>..HEAD`。先确认边界存在且是目标提交的祖先；非祖先、缺失或无法确认时，不用该范围推断完整性。
3. 结合最新版本块及必要的相邻版本块，核对提交哪些已写、哪些遗漏。提交信息不足以判断用户可见行为时定点检查对应提交或代码；不凭标题猜测，不把纯内部重构强行写成新功能。
4. 历史日志目前可能完全没有提交边界；此时版本日期和提交日期不能证明对应关系。读取有限的相关提交和日志进行初步比对，无法可靠确定起点时向用户说明并询问核对范围或基准提交；不得声称已完整覆盖或写入未经确认的边界。
5. 按用户指定的版本补充遗漏；未指定时先判断是更新现有最新版本还是新建发布版本，存在歧义则询问。避免重复记录，保留已有文本和文件编码；不顺带修改其他版本。
6. 仅在整个目标提交范围已核对完毕且版本归属明确时，将该版本边界设为实际核对到的完整提交哈希。工作区未提交变更不在 `git log` 范围内，如可能影响日志完整性则提示用户。
7. 报告新增内容、核对范围及无法确认的部分；单独执行更新日志时不自动打包，任何情况下均不自动提交或发布。
